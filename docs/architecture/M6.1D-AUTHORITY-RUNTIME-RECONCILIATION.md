## Cadena de autoridad que se preserva

```text
Product Trust Root / Deployment Trust
        ↓ Trust Bundle firmado y anclado
M4 Center Authority / Enrollment Authority
        ↓ binding @1.0.0, scopes, issuer, kid, epoch, vigencia
Site Runtime Authority operacional histórica de Aegis
        ↓ JWS, delegation, LKG, staging A/B, fencing
Site Core local → identidad/terminal → capability → datos locales
        ↓ transporte separado
outbox/inbox, sync, fallback autorizado y estado observado
```

Sync, WAN, NTP y estado observado no se convierten en una fuente de permisos.
La clave histórica de Site Runtime continúa siendo operacional durante la
transición; M4 autentica su origen mediante el binding existente y no se crea
otra Site Authority.

## Hallazgos de seguridad vs. mejoras de producto

### Hallazgos materiales resueltos en esta fase

1. El daemon de Authority sólo tenía `Uninitialized`/`TestFixture`; ahora puede
   cargar una jerarquía durable mediante referencias a claves selladas y
   persistir estado público atómicamente tras cada operación aceptada.
2. `/health` no distinguía proceso vivo de autoridad inicializada; ahora
   informa `authorityState` y conserva `UNINITIALIZED`/`UNAVAILABLE` como
   estados no listos.
3. Site Core verificaba el Trust Bundle con `currentEpoch=0`; ahora consulta y
   actualiza su high-water mark durable sólo después de verificar el material.
4. El trust mode legacy/M4 no se conservaba de forma independiente a la URL;
   ahora existe una migración durable y el publisher no hace downgrade
   silencioso.

### Mejoras acotadas, no defectos nuevos

- timeout/correlation/reintentos acotados en el cliente HTTP;
- fixture golden compartido para canonicalización;
- UI más explícita para estados de bootstrap/capability;
- pruebas de crash y atomicidad de journal.

## Plan de corrección aplicado en M6.1D

1. Añadir serialización durable pública del Authority Service, carga
   verificable tras reinicio y commits atómicos; no crear claves si falta una
   ceremonia.
2. Añadir loader de sealing-key por archivo protegido, sin persistir la clave
   de autoridad ni devolver secretos por API.
3. Separar `/health` de readiness y exponer bootstrap/capability status seguro.
4. Añadir HWM de Trust Bundle en Site Core y consumirlo en instalación/reinicio.
5. Añadir trust mode persistente M4/legacy en el publisher, con downgrade
   bloqueado cuando el deployment ya exige M4.
6. Endurecer el transporte Center ↔ Authority con timeout, request ID,
   idempotency key, scope/capability y errores seguros.
7. Añadir golden vector y regresiones para epoch, digest, revocación,
   transport, reload, caller binding, idempotencia durable y enrollment sin
   consumo ante preflight fallido.

## Límites explícitos

- La raíz Product Trust productiva no se genera ni se importa en esta fase.
- La ceremonia Owner/AAL2 tiene un plan durable protegido por RPC AAL2, pero
  la generación offline, custodia y activación productivas siguen pendientes.
- No se desplegaron cambios al NAS, no se consumieron tickets, no se inició
  enrollment y no se modificaron Center/Aegis remotamente.
- El payload histórico de Aegis permanece fuera de Node Manager y no fue leído
  como fuente ni regenerado.
